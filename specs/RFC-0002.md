## Motivation

Users need matrix-style tables where a final "summary" row aggregates data
across all rows above it — for example a **Running Balance** row in an expenses
sheet. The current MDXTab model supports:

- **Computed columns**: per-row expressions (row-scoped).
- **Aggregates**: whole-column scalars interpolated into body text.

Neither mechanism can produce a synthetic table row whose cells may reference
other cells *in the same row* (e.g., cumulative sums that carry forward from
the previous period column).

---

## Decision

Add a `summary_rows` section to the table frontmatter. Each summary row is a
map of **cell expressions** that are evaluated left-to-right. Cells may
reference:

- Existing aggregate functions (`sum(col)`, `avg(col)`, etc.) over data rows.
- Earlier cells in the same summary row via `self.<column>`.

### Chosen approach: Cells-as-Expressions with `self` references (Option A)

```yaml
summary_rows:
  running_balance:
    label: Running Balance
    cells:
      p1: sum(p1)
      p2: self.p1 + sum(p2)
      p3: self.p2 + sum(p3)
      p4: self.p3 + sum(p4)
      p5: self.p4 + sum(p5)
```

### Evaluation rules

1. Cells in a summary row are evaluated in **declaration order** (YAML key
   order, left to right).
2. `self.<col>` resolves to the already-evaluated value of column `<col>` in
   the same summary row. Referencing a column that has not yet been evaluated
   is an error.
3. `sum(<col>)`, `avg(<col>)`, `min(<col>)`, `max(<col>)`, `count(<col>)`
   aggregate over **data rows only** (not other summary rows).
4. Expressions use the same language as computed columns and aggregates.
5. Null/empty data cells are treated as `0` for numeric aggregation (consistent
   with existing aggregate behavior).
6. Summary rows are appended at the bottom of the table in the rendered preview
   only — source markdown is not modified.

### Frontmatter schema

```yaml
tables:
  <tableName>:
    columns: [...]
    computed: { ... }
    aggregates: { ... }
    summary_rows:                         # NEW
      <rowKey>:
        label: <string>                   # required — first-column display text
        cells:                            # required — map of column → expression
          <columnName>: <expression>
```

- `label` is the value shown in the first (key/name) column of the summary row.
- `cells` maps column names to expressions. Columns not listed render as empty.
- Multiple summary rows are allowed and render in declaration order.

### Rendering

Summary rows are injected into the rendered markdown after the last data row,
before any aggregate interpolation. Each summary row becomes a standard pipe-
delimited markdown row matching the table's column count.

---

## Alternatives considered

### Option B: Aggregate-to-aggregate chaining

Define cumulative values as regular aggregates that reference each other, then
map them into a summary row:

```yaml
aggregates:
  run_p1: sum(p1)
  run_p2: run_p1 + sum(p2)
summary_rows:
  running_balance:
    label: Running Balance
    cells: { p1: run_p1, p2: run_p2, ... }
```

**Rejected** because it duplicates definitions across two sections and forces
the user to name intermediate scalars that exist only to be laid out in a row.

### Option C: Dedicated `running_sum` helper

```yaml
summary_rows:
  running_balance:
    label: Running Balance
    columns: [p1, p2, p3, p4, p5]
    formula: running_sum
```

**Rejected** because it only solves one pattern. Any non-cumulative-sum summary
(averages, conditional logic, weighted calculations) would need yet another
dedicated helper. Option A is generic enough to express all of these.

### Option D: `scan` shorthand sugar

A `scan` keyword that expands into Option A internally:

```yaml
summary_rows:
  running_balance:
    label: Running Balance
    scan: [p1, p2, p3, p4, p5]
    cell: self.prev + sum(col)
```

**Deferred**, not rejected. If verbose `cells:` maps become painful in practice,
`scan` can be added later as syntactic sugar that expands to Option A at parse
time.

---

## Consequences

- The expression evaluator gains a new resolution scope (`self`) for summary
  row evaluation only.
- Frontmatter parsing/validation adds a `summary_rows` section.
- The rendering pipeline adds a summary-row injection step after computed-column
  injection.
- No changes to the existing computed-column or aggregate models.
- Future `scan` sugar (Option D) can be layered on without breaking changes.
